# Auto Agent Rust 简历项目介绍与面试准备

## 一句话项目介绍

Auto Agent Rust 是一个基于 **Rust + Axum + React + TypeScript** 构建的企业级 AI Agent 平台，支持 SSE 流式对话、MCP 动态工具调用、Skills 能力扩展、多用户权限隔离、Hermes 风格工具结果上下文压缩，以及可配置的人在回路（HITL）审批机制。

## 简历项目描述

**Auto Agent Rust｜AI Agent 平台 / Rust 后端 / React 前端**

- 负责从原有系统中重构并实现一套纯 **Rust + React + TypeScript** 的 AI Agent 平台，后端基于 Axum 提供 Agent Run / Stream、Memory、Skills、MCP、Harness 观测等核心接口，前端提供聊天、设置、工具权限、技能管理与审批交互界面。
- 设计并实现 **MCP 动态工具注入与调用链路**，支持将外部 MCP Server 的工具自动注册为 `mcp_*` 工具，并在 Agent 推理过程中统一调度本地工具与远程 MCP 工具。
- 实现 **多用户权限管理体系**，支持不同用户配置不同 MCP 工具与 Skills 的 allowlist / denylist，使用户只能看到并调用其授权范围内的工具和技能。
- 对齐 Hermes Agent 的上下文管理思路，实现 **大工具结果落盘 + 预览摘要入上下文** 机制，避免模型中间工具调用结果无限膨胀上下文；通过 `tool_result_size_chars`、`tool_turn_budget_chars`、`tool_result_preview_chars` 控制单工具和单轮工具结果预算。
- 设计并落地 **HITL（Human-in-the-loop）人在回路审批机制**，支持通过配置文件和设置界面定义哪些工具或工具前缀需要人工确认；前端可对高风险动作进行 approve / reject / 修改参数后 approve。
- 将系统提示词、模型参数、Max Tokens、MCP 权限、Skills 权限、HITL 策略等核心运行参数纳入 `config.yaml` 与前端设置页统一管理，提升系统可配置性和可运维性。
- 建立测试与验证流程，覆盖 Rust 后端单元测试、前端 Vitest 测试与构建验证，保障权限控制、上下文压缩、HITL 审批和流式事件链路的稳定性。

## 项目亮点

### 1. Rust + React 的 Agent 平台化重构

项目不是简单调用大模型 API，而是将 Agent 的运行链路拆成后端服务、前端交互、工具系统、MCP 接入、Skills 管理、记忆管理和审批系统等模块，具备平台化扩展能力。

### 2. MCP 动态工具与用户级权限隔离

系统可以从 MCP Server 动态拉取工具并注入 Agent 工具列表，同时在用户维度进行 allowlist / denylist 过滤。这样既保留 MCP 扩展能力，也避免所有用户默认拥有所有工具权限。

### 3. Hermes 风格上下文压缩

传统 Agent 容易把每次工具调用的完整结果塞回上下文，导致 token 快速膨胀。项目对大工具结果进行落盘，只把预览和路径返回给模型，必要时模型再读取文件，兼顾可追溯性和上下文成本。

### 4. 可配置 HITL 人在回路

通过配置文件或设置界面定义哪些行为需要人工介入，例如写文件、编辑文件、删除类 MCP 工具、外部系统操作等。审批时可以通过、拒绝，也可以修改参数后再通过，适合高风险 Agent 场景。

### 5. 配置化与可运维性

模型 ID、Base URL、Max Tokens、系统提示词、工具结果预算、权限策略、HITL 策略都集中在 `config.yaml`，同时前端提供可视化配置入口，方便部署和运营。

### 6. 完整验证意识

项目变更后通过 Rust 单元测试、前端测试和构建验证，体现了对 AI Agent 系统稳定性、权限安全和用户交互一致性的工程保障。

## 面试高频问题与参考回答

### 1. 这个项目解决了什么问题？

它解决的是 AI Agent 从 Demo 到可控平台化落地的问题。普通 Agent 只关注能否调用工具，但实际使用时还需要权限隔离、上下文控制、人工审批、配置化和可审计。这个项目围绕这些问题构建了一套 Rust 后端和 React 前端的 Agent 执行框架。

### 2. 为什么后端选择 Rust？

Rust 适合构建长时间运行、并发请求和高可靠性的后端服务。Agent 平台需要处理 SSE 流式连接、工具调用、文件读写、MCP 请求和状态管理，Rust 的类型系统、所有权模型和 Tokio 异步生态可以帮助减少运行时错误，并提升服务稳定性。

### 3. Axum 在项目中扮演什么角色？

Axum 负责提供 HTTP API 和 SSE 流式接口，包括 Agent Run / Stream、Memory、Skills、MCP、Harness、设置保存等。它基于 Tokio 和 Tower 生态，适合构建异步后端服务。

### 4. MCP 是怎么接入的？

后端会连接配置中的 MCP Server，获取可用工具列表，并将远程工具统一封装成 `mcp_*` 命名的 Agent 工具。模型调用这些工具时，后端再把调用转发到 MCP Server，并将结果返回给 Agent 流程。

### 5. 为什么 MCP 工具需要权限管理？

因为 MCP 工具可能包含文件操作、数据库操作、网络请求、内部系统调用等高风险能力。如果所有用户都能看到和调用全部工具，会有明显安全风险。所以系统增加了用户级 allowlist / denylist，保证不同用户只拥有自己需要的工具能力。

### 6. Skills 权限和 MCP 权限有什么区别？

MCP 权限控制的是工具能力，也就是 Agent 可以调用什么外部动作；Skills 权限控制的是提示词和工作流能力，也就是用户可以加载哪些能力模板。前者更偏执行权限，后者更偏认知和流程权限。

### 7. allowlist 和 denylist 同时存在时应该怎么理解？

通常 allowlist 用来定义用户可访问范围，denylist 用来显式排除危险项。工程上可以采用“先按 allowlist 收缩范围，再用 denylist 排除”的方式，这样既能表达默认授权范围，也能快速禁止某些工具。

### 8. 什么是 Hermes 风格的上下文管理？

它的核心思想是不要把所有中间工具结果都完整塞进模型上下文。大结果应该落盘或外部存储，模型上下文只保留摘要、预览和引用路径。这样可以降低 token 消耗，避免无关长文本污染模型注意力，同时保留可追溯能力。

### 9. 你们怎么判断工具结果是否应该进入上下文？

项目中提供了几个配置项：`tool_result_size_chars` 控制单个工具结果超过多大就落盘；`tool_turn_budget_chars` 控制单轮工具结果总预算；`tool_result_preview_chars` 控制落盘后仍保留在上下文中的预览长度。超过预算的大结果会优先被落盘。

### 10. HITL 是怎么设计的？

HITL 分为策略匹配、审批请求、前端交互和结果回传四步。工具调用前先经过策略匹配，如果命中需要审批的规则，就通过 SSE 发出 `approval_required` 事件；前端展示审批卡片；用户可以 approve、reject 或修改参数后 approve；后端收到结果后继续或终止该工具调用。

### 11. HITL 的配置规则有哪些？

主要支持按 `tool` 精确匹配和按 `tool_prefix` 前缀匹配。例如：

```yaml
hitl:
  enabled: true
  default_action: "auto"
  timeout_seconds: 300
  rules:
    - tool: "write_file"
      require_approval: true
      risk_level: "high"
    - tool_prefix: "mcp_"
      require_approval: true
      risk_level: "medium"
```

### 12. `default_action` 是什么意思？

`default_action` 表示没有命中任何 HITL 规则时如何处理：

- `auto`：自动执行。
- `require_approval`：默认也需要人工审批。
- `reject`：默认拒绝执行。

生产环境中，如果工具风险较高，可以把默认策略调成 `require_approval`，再对白名单工具单独放行。

### 13. `risk_level` 会影响执行逻辑吗？

当前更主要用于前端展示、审计和风险提示，例如 low / medium / high。真正决定是否审批的是 `require_approval`、规则匹配和 `default_action`。后续也可以扩展成不同风险等级对应不同审批流程。

### 14. 如果 MCP 工具需要确认，tool 应该怎么写？

如果想让所有 MCP 工具都进入审批，可以写：

```yaml
- tool_prefix: "mcp_"
  require_approval: true
  risk_level: "medium"
```

如果只审批某个 MCP 工具，需要写后端注册后的完整工具名，一般形式类似：

```yaml
- tool: "mcp_<endpoint_key>__<original_tool_name>"
  require_approval: true
  risk_level: "high"
```

实际使用时，可以先用 `tool_prefix: "mcp_"` 观察前端审批卡片里的真实工具名，再收敛成精确规则。

### 15. 为什么 HITL 要支持“修改参数后通过”？

因为很多时候工具意图是对的，但参数需要调整。例如模型想写文件到错误路径、删除范围过大、调用 MCP 工具时参数不够安全。允许审批人修改参数后通过，可以避免简单拒绝导致任务中断，也能保留人的控制权。

### 16. SSE 流式输出在项目中有什么作用？

SSE 不只用于展示模型 token，还用于推送工具调用、工具结果、审批请求、审批结果、错误事件等过程信息。这样前端可以实时展示 Agent 的中间步骤，并在需要 HITL 时暂停等待用户操作。

### 17. 非流式接口能不能支持 HITL？

理论上可以，但体验不好，因为审批需要一个持续交互通道。项目中更推荐在流式模式下使用 HITL：后端通过 SSE 发出审批事件，前端及时展示审批卡片并回传结果。非流式模式遇到审批时可以提示用户切换流式模式。

### 18. 系统提示词为什么要放到 config.yaml？

系统提示词是 Agent 行为边界的一部分，经常需要根据部署环境、输出目录、安全要求和工具能力调整。放入配置文件后，可以在不改代码的情况下变更 Agent 行为，也方便审计和版本管理。

### 19. 前端设置页为什么重要？

因为很多 Agent 参数不应该只由开发者改代码来调整，例如模型参数、Max Tokens、MCP 权限、Skills 权限和 HITL 策略。设置页让管理员可以可视化配置，提高系统可运维性。

### 20. 项目中有哪些安全边界？

包括本地文件工具的工作区限制、MCP 工具用户级权限过滤、Skills 加载权限、HITL 高风险工具审批、大工具结果落盘而不是盲目进入上下文，以及配置化的系统提示词约束。

### 21. 你如何保证 Agent 不会越权调用工具？

核心是工具列表在暴露给模型之前就按用户权限过滤。模型看不到未授权工具，自然无法按常规工具调用链路调用。同时后端执行层也应该再次校验权限，避免只依赖前端或 prompt 约束。

### 22. 如果用户修改前端请求绕过权限怎么办？

权限不能只放在前端，必须在后端执行层校验。即使用户伪造请求，后端也应根据 user id 和配置策略判断该工具是否可用，不允许执行未授权工具。

### 23. 这个项目最大的技术难点是什么？

难点不在于单次调用大模型，而在于把 Agent 的完整执行过程工程化：工具动态注册、权限过滤、流式过程展示、上下文预算、人工审批、配置持久化和前后端状态同步都要串起来，并且要保证失败时可恢复、可解释。

### 24. 如果让你继续优化，你会做什么？

可以继续做四个方向：

1. 把 HITL 审批记录做成更完整的审计日志和回放能力。
2. 支持角色 RBAC，而不只是用户级 allowlist / denylist。
3. 对工具结果做结构化摘要和向量检索，而不仅是预览加路径。
4. 为 MCP 工具增加风险自动识别，例如根据工具 schema、名称和参数判断风险等级。

### 25. 这个项目体现了你的哪些能力？

体现了 Rust 后端开发、React 前端开发、AI Agent 架构设计、MCP 工具生态接入、权限系统设计、上下文工程、SSE 流式交互、HITL 安全机制和工程测试验证能力。

## 面试追问准备

### 追问：如果 allowlist 为空代表什么？

建议回答：这取决于系统设计，可以有两种语义：一种是空表示不限制，另一种是空表示无权限。企业安全场景我更倾向于显式配置语义，并在配置中区分 `null` 和空数组，避免误解。

### 追问：HITL 审批超时怎么办？

建议回答：可以由 `timeout_seconds` 控制。超时后根据安全策略处理，通常高风险动作应该默认拒绝，低风险动作可以根据配置自动执行或失败返回。生产环境我会倾向 fail closed。

### 追问：工具结果落盘会不会导致模型看不到关键信息？

建议回答：会有这个风险，所以不能只返回路径，还要返回足够的 preview / summary。后续可以做更智能的摘要、结构化提取，或者允许模型按需读取落盘文件中的相关片段。

### 追问：MCP 工具名为什么要加前缀？

建议回答：前缀可以避免本地工具和远程工具重名，也方便权限策略和 HITL 规则按命名空间匹配，例如统一用 `mcp_` 识别远程工具。

### 追问：为什么不用 WebSocket？

建议回答：当前主要是服务端向前端推送 Agent 事件，SSE 更简单，和 HTTP 基础设施兼容性好，断线重连也方便。如果后续需要更复杂的双向实时协作，可以再引入 WebSocket。
